# infra/tofu — OpenTofu for Kiorex Passport

Implements ADR-028 / KX-21 §01. OpenTofu **1.13.9** (`.opentofu-version`), `hashicorp/aws ~> 6.0`. **Nothing in this
tree has been applied.** Do not deploy until the founder approves the first deploy.

```
.opentofu-version   .tflint.hcl
modules/contracts/README.md      inputs/outputs of the 10 contracts
modules/aws/{network,database,container-service,object-storage,cdn-edge,secrets,email,dns-certs,waf,observability,ci-oidc}
modules/aws/identity/     (this repo only) Cognito user pool, triggers, app clients, domain, back-channel registry
modules/product-stack/    one product in one cell (precondition: provider region == platform/data-cells.json)
live/{staging,prod}/frankfurt/kiorex-account/    backend.tf main.tf variables.tf outputs.tf terraform.tfvars
```

`modules/` is a verbatim copy of the Kiorly Clinic skeleton (KX-22). Fix a module in `clinics-management` first, then re-copy.

## State
S3 (`kiorex-tofu-state-<env>-euc1`, native `use_lockfile`) + OpenTofu client-side KMS encryption (`alias/kiorex-tofu-state`)
for state **and plan** files. One state per product / environment / cell. Backend config cannot use variables, so the
bucket names are literal in each `backend.tf`.

## 1. Bootstrap (platform admin, once per account, locally with SSO/MFA)
State buckets, KMS key and GitHub roles are created by **`clinics-management/infra/tofu/bootstrap`** (one set per AWS account,
roles already trust this repo). Run it there first; nothing to bootstrap here.

## 2. Plan (local, same as CI)
```sh
export AWS_PROFILE=aws-kiorex-profile      # eu-central-1
cd infra/tofu/live/staging/frankfurt/kiorex-account
tofu init
tofu fmt -check -recursive && tofu validate
tflint --recursive && trivy config .
tofu plan -var "git_sha=$GIT_SHA" -out plan.tfplan
```
Offline checks (no AWS): `tofu fmt -recursive && tofu init -backend=false && tofu validate` in every live directory.

## 3. Apply
Never from a laptop except documented break-glass; use `deploy.yml` (staging) and `release.yml` (production, approval).
Image first: an App Runner service needs its image, so the first apply is two-phase —
`tofu apply -target=<module>.module.container_service.aws_ecr_repository.this`, push the image tagged `$GIT_SHA`, then the full apply
(the workflows do this).
`prod` tfvars carry `aws_account_id = "REPLACE_WITH_PROD_ACCOUNT_ID"` on purpose: **NEEDS_HUMAN** decide the production
account (HB05); the validation fails until then. Staging targets the Kiorex account 599243104052.

## 4. Adopting existing resources (migration path T4-alt)
If real data already lives in the CDK stack: set CDK removal policies to RETAIN, then add `import` blocks, e.g.
```hcl
import {
  to = module.account_service[0].module.database[0].aws_db_instance.this
  id = "<existing-rds-identifier>"
}
```
(also VPC, S3 buckets, KMS keys), run `tofu plan` until it shows **0 changes**, `cdk destroy` the stateless rest, recreate those
with OpenTofu. Prefer greenfield (T4) while there are no live tenants.

## 5. GitHub Actions (`.github/workflows`)
`infra-plan.yml` (PR: fmt, validate, tflint, trivy, plan with read-only `tofu-plan`), `deploy.yml` (staging),
`release.yml` (production), `drift.yml` (nightly). **All apply workflows are `workflow_dispatch` only** until the founder
approves the first deploy. Repository variables: `AWS_TOFU_PLAN_ROLE_ARN`, `AWS_TOFU_APPLY_STAGING_ROLE_ARN`,
`AWS_TOFU_APPLY_PROD_ROLE_ARN` (from bootstrap outputs); GitHub Environments `staging` and `production` (required reviewers).

## Known blockers
- AWS Organization SCPs: in account 599243104052, user `cursor-admin` gets explicit denies on `cloudformation:ListStacks`,
  `apprunner:ListServices`, `rds:DescribeDBInstances`, `s3:ListAllMyBuckets`. The org admin must relax them before plan/apply.
- HB07: with App Runner VPC egress and no NAT, calls to third-party APIs need a path — verify in staging; add a NAT or egress proxy.
- tflint is not installed locally; config is kept and runs in CI. App Runner log retention is set by the AWS CLI via a
  `terraform_data` provisioner (the service owns those log groups) — runners need the AWS CLI.

### Identity stack notes (managed IdP = Amazon Cognito, branded **Kiorex Passport**)
- Clients, scopes, claims and token lifetimes are read from `config/idp.json` (`environments.staging` / `environments.production` only; local is ignored).
  Clients whose redirect URIs are still `TODO_NEEDS_HUMAN` are skipped until filled. Confidential client secrets are generated by Cognito and written to Secrets Manager (never output).
- OTP triggers: placeholders by default. For the real handlers build `packages/otp-sender/src/lambda.ts` (esbuild -> zip, handlers
  `lambda.defineAuthChallenge|createAuthChallenge|verifyAuthChallengeResponse`) and pass `-var otp_bundle_path=<zip>`; set non-secret
  `otp_extra_env` (`WA_PHONE_NUMBER_ID`, `WA_TEMPLATE_AR/EN`). The WhatsApp access token must come from Secrets Manager (NEEDS_HUMAN: code currently reads `WA_ACCESS_TOKEN` from env).
  The `000000` bypass is wired only when `test_otp_enabled` (staging; guarded by a precondition against prod).
- Custom domain `account.kiorex.com`: ACM in us-east-1 + alias record are created, but Cognito requires `kiorex.com` to already resolve (A record) — apply `live/prod/global/dns` and publish an apex record first. Staging uses a Cognito prefix domain (`account.staging.kiorex.com` per KX-19 is NEEDS_HUMAN).
- `account_service_enabled` (default false) adds an optional small App Runner (Passport web / OTP sender / back-channel dispatcher), no DB, no CDN.

### Known Cognito gaps (design decisions needed)
1. **No native OIDC back-channel logout.** `session.revoked` / `subject.deleted` need a small revoke service (the optional account service)
   that signs `logout_token`s with KMS and POSTs them to the registry in SSM `/kiorex/account/<env>/backchannel-logout-clients`.
2. **`aud` must be `kiorex-api`.** Cognito access tokens carry `client_id`, not `aud`; the pre-token-generation trigger can set it only if Cognito allows
   (`set_access_token_aud`, default off — verify in staging) otherwise Kiorex API must validate scope `kiorex-api/access` + `client_id`.
3. **Refresh-token rotation/reuse detection** depends on the user-pool tier/feature plan; `idp.json` requires rotation with reuse detection — confirm on the chosen tier.
4. **Hosted UI / managed login does not support CUSTOM_AUTH** (phone OTP challenge). The Passport sign-in UI must drive `InitiateAuth` itself (account service) or switch to Cognito native passwordless SMS_OTP + passkeys with a custom SMS sender.
5. **TOTP for privileged roles (KA-03)**: pool MFA is OPTIONAL with software tokens; per-role enforcement is a step-up in the account service.

## 7. Demo-data seeding on staging (Q10, non-production only)
Passport on AWS is Cognito, so the seed is a script, not a Lambda: `scripts/seed-cognito-demo.mjs` (AWS SDK only in `scripts/adapters/`). `live/staging/**/demo_seed.tf` adds the least-privilege IAM policy `<name>-cognito-demo-seed` (and an optional assumable role for `demo_seed_principal_arns`) when `enable_demo_seed = true`; `live/prod/**/demo_seed.tf` makes a stray `true` fail the plan. The staging `test_phone_numbers` lists every demo persona (fixed OTP `000000`, staging only; the identity module already fails a prod plan with `test_otp_enabled`). Output `demo_seed_invoke` prints the command; `scripts/seed-staging.sh` (workspace root) runs it as step 1. The product-stack module copy also carries `demo_seed.tf` (unused here: the account service has no database).
